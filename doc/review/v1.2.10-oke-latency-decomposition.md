# v1.2.10 OKE Latency Decomposition -- "Why is OKE slow?"

Date: 2026-07-04
Scope: per-request latency of the OKE stack (esquire.mir0n.pro) vs the two local stacks, measured
with the Observability Stack (doc/Esquire.ObservabilityStack.md).

## Method

The Observability Stack splits each request into five bands: `net` (client<->gateway), `gw_self`
(gateway's own CPU: JWT, token relay, response buffering), `in_cluster` (gateway<->service hop),
`srv_self` (service logic), `srv_inner` (DB / JPA). `hauberk run entity-smoke --metrics` fires the
load; the gateway always emits `net` + `gO` (whole server-side); the per-service split (`sO`/`sI`)
appears only when the gateway Master Switch (`GW_SERVICE_METRICS_ENABLED`) is ON.

All figures in this doc are RUNNING-HOT: measured with the master switch OFF (it buffers the response
body and only distorts timings) after the request paths are warmed. Cold first-hit timings were
checked separately and are only mentioned, not tabulated (see "Warm-up").

## The production picture (switch OFF, warm)

Per request, OKE, steady warm state, client-total = server-side + RTT:

    request                     RTT (net)   server-side (warm)   client total
    reads (cache / lookups)      ~55 ms       ~15-35 ms            ~80-100 ms
    writes (create / deposit)    ~55 ms       ~45-105 ms           ~95-165 ms

Where the server-side goes:

- `net` ~55 ms -- the Toronto RTT, on every request, the single biggest band on a read. Loopback +
  port-forward locally is ~5 ms. Geography; not fixable from a remote client.
- `gw_self` ~2 ms -- the gateway's own work is tiny in production. (An earlier switch-ON measurement
  showed 12-51 ms, but that was the switch's response-body buffering, amplified on the weak node -- a
  measurement artifact, not a production cost.)
- `in_cluster` -- the gateway<->service hop. This is the one genuine node cost: on OKE the two
  replicas sit on DIFFERENT nodes (topologySpread), so the call is a real cross-node hop over the
  Flannel overlay, vs a same-host bridge locally. It is CPU/network bound on the tiny nodes.
- `srv_self` / `srv_inner` -- service logic and DB. On READS these match the local box to the
  millisecond (logic ~2-3 ms, DB ~0, cache-served). On WRITES they carry the real work, and the
  heavy part is warm-up (below), not a standing OKE tax.

Bottom line: OKE is not slow because of Esquire's code or the DB -- those bands match local. It is
slow because it is a continent away (~55 ms fixed RTT) and the Always-Free 1-OCPU ARM nodes make the
cross-node hop costlier than a dev box. The write cost is dominated by JVM warm-up, which real
traffic amortizes for free.

## Warm-up (mentioned, not the focus)

Cold first-hit paths run several times slower until the JVM JITs and one-time init (JPA statement
prep, class loading) is paid down -- e.g. a cold deposit is ~450 ms server-side vs ~45 ms once hot.
It warms in a single pass and real traffic keeps paths hot, so cold timings only appear for the first
caller right after a pod restart. All figures in this doc are running-hot; cold numbers are not
carried further.

## Would bigger nodes be worth it?

Bigger nodes touch ONLY the CPU/hop cost -- the genuine `in_cluster` cross-node hop and the warm
write CPU. They cannot move `net` (geography), the cold-start spikes (that is warm-up, amortized for
free by traffic), or the DB (already local-fast). On the warm production numbers:

- Read (~90 ms): ~55 ms RTT + ~35 ms server. Collapsing the node cost to local (~10 ms) -> ~70 ms.
  Saves ~20 ms, still RTT-bound.
- Write (user, ~165 ms): ~55 ms RTT + ~105 ms warm server. Faster cores cut the CPU-bound server
  most -> perhaps ~90-100 ms. Saves ~65-75 ms -- writes benefit most.

So bigger nodes help WRITES noticeably and reads only modestly, and every request keeps a hard
~55-60 ms RTT floor no node size removes.

Verdict: NOT worth leaving the free tier for the demo/portfolio site. The dominant cost (RTT) is
untouched by node size; the write cost is mostly warm-up (free); the residual node tax is only
perceptible on writes. Cheaper, free levers matter more:

- HTTP keep-alive on the client -- avoids the repeated TLS handshake (~100 ms per new connection,
  seen in the earlier curl test); a far bigger win than node size for a real browser session.
- Client proximity / CDN -- the only thing that actually moves `net`, and only if it ever matters.

Bigger (paid) nodes become justified only if OKE turns into a real, write-heavy, multi-user
production system -- not for the current single-region demo.

## Concrete levers for the CPU/hop cost

Free -- and honestly, none of these move steady-state latency on THIS cluster:

1. Native-image the gateway (GraalVM / Spring AOT). Does NOT buy latency -- production `gw_self` is
   already ~2 ms (switch off). What it buys is startup ~50 ms (faster rollout / failover), ~half the
   memory (relief on the packed 6 GB nodes), and no JIT warm-up (the cold first-hit write spikes
   disappear). Cost: GraalVM AOT metadata for Spring Cloud Gateway + Security + token-relay filters,
   per-arch native builds (we ship ARM + x86), longer CI, harder debugging, less mature native path.
   A code/build change, not a flag. See the HA note below. Optional; modest payoff for a demo.
2. Topology routing does NOT apply here. `trafficDistribution: PreferClose` routes by
   `topology.kubernetes.io/zone`, but all four OKE nodes are in a SINGLE availability domain
   (CA-TORONTO-1-AD-1 -- Toronto has one AD, free tier is single-AD), so PreferClose sees every node
   as equidistant and is a no-op. `internalTrafficPolicy: Local` IS node-local but hard-drops when a
   gateway has no service replica on its own node -- guaranteed with x2 spread across 3 nodes. So
   there is no SAFE free lever to collapse `in_cluster` on this topology.
3. Keep the gateway->service connection pool warm / HTTP keep-alive -- already done (R1
   `gwPoolMaxConnections=64`); no per-request TCP/TLS in the hop.
4. Master switch OFF in prod (done) -- it was the main thing inflating `gw_self` when measured.

Net free result: latency stays essentially as-is (RTT-bound). Staying free loses nothing (the x2
setup is stable, HA, e2e-green) but gains no meaningful latency, because RTT and the residual
write-path CPU cost are both money problems on this topology.

Paid / infra:

5. Swap A1 ARM -> x86 E-series nodes (E4/E5 AMD), or more OCPU per node so pods are not CPU-starved.
   The bottleneck is single-thread speed; E-series cores are ~2-3x faster per thread than A1 Ampere.
   If money is spent, spend it here -- not on more of the same ARM. This is the only lever that
   touches the residual `in_cluster` + warm-write CPU cost.
6. OKE VCN-native pod networking instead of Basic+Flannel -- drops VXLAN encapsulation on the
   cross-node hop. A cluster rebuild, not a flag. (A second AD would also make PreferClose viable, but
   multi-AD is not available on the Toronto free tier.)

## Does a native gateway keep the same HA?

Short answer: HA (redundancy / failover) is unchanged -- it is a deployment property, not a
JIT-vs-AOT property. A native image is still a container you run x2, spread across nodes, with probes
and rolling updates, exactly like the Spring JVM gateway. Native actually IMPROVES failover recovery:
it starts in ~50 ms vs the JVM's multi-second warm-up, so a replacement pod restores redundancy
almost instantly and shrinks the degraded window.

What native trades is NOT availability but:

- Peak-throughput headroom -- a fully warmed JIT JVM (C2 compiler) can reach a higher top-end req/s
  than a native image (no runtime profile-guided optimization). Under a failover that doubles load
  onto one survivor, the JIT instance has more ceiling. At our demo load this is irrelevant (nowhere
  near either ceiling); it matters only at high sustained throughput.
- Maturity / dynamism -- Spring Cloud Gateway's native path is less battle-tested than the JVM path;
  reflection-heavy filters need AOT metadata, and dynamic route refresh is more limited.

So "native gives up HA" is understandable but, strictly, wrong: availability and failover are
equal-or-better. What you give up is throughput headroom and some runtime maturity -- a robustness/
scale trade, not an availability one. For a low-traffic demo, native is HA-equivalent to the Spring
gateway with faster restarts.

## Best approach with unlimited budget -- and what it costs

The dominant cost is RTT, and the ONLY thing money buys that moves RTT is putting an origin near the
viewer. So the no-compromise design is:

Tier A -- one strong region (kills the node/warm cost, not the RTT):

- 3 worker nodes, x86 E5 Flex, 4 OCPU / 32 GB each (real headroom, x2 everything, zero contention)
  -> the residual `in_cluster` + warm-write CPU cost collapses to near-local.
- Flexible load balancer, Enhanced OKE cluster, block storage.
- Approx OCI list price: compute ~12 OCPU x $18/mo + ~96 GB x $1.1/mo ~= $325; + Enhanced cluster
  $73; + LB $8; + storage ~$5. Total ~ $400-420 / month.
- Result: writes lose the CPU cost (~50-70 ms faster warm); reads still ~55 ms RTT-bound. Front with
  Cloudflare (free-$20/mo) for static assets / edge TLS.

Tier B -- multi-region (the only way to buy down RTT globally):

- The Tier A stack replicated in ~3 regions near the audience + global geo-routing (OCI Traffic
  Management / DNS, or Cloudflare load balancing) so each viewer hits the nearest origin.
- Approx: ~3 x Tier A compute (~$975) + geo-DNS / traffic-mgmt + cross-region data ~= $1,100-1,300 /
  month.
- Result: `net` drops from ~55 ms to ~10-20 ms for viewers near any region -- the only lever that
  actually shrinks the dominant band.

(List prices, approximate, single-region ca-toronto-1 basis; commit / UDR discounts and egress not
included.)

Recommendation at unlimited budget: Tier B if a globally-fast experience is the goal; Tier A if the
audience is regional. The diminishing-returns curve stands: $0 -> ~$400/mo buys the node/warm cost
back (mostly a write-path win); ~$400 -> ~$1.2k/mo is the only step that buys down the ~55 ms RTT,
and only for a spread-out audience. For the current single-region portfolio demo, the free tier is
the right economic choice.

## One-line takeaway

The slowness is transport and warm-up, not the application: ~55 ms is fixed Toronto RTT, the write
cost is JVM warm-up that real traffic amortizes for free (deposit 446 -> ~45 ms server-side once
warm), and the only standing node cost is the cross-node hop -- while service logic and DB match the
local box exactly. On this single-AD free-tier cluster no free lever meaningfully moves latency;
both real costs (RTT and the residual write CPU) are money problems, and for a single-region
portfolio demo the free tier is the right call -- it loses nothing and the paid gains are not worth
it.
