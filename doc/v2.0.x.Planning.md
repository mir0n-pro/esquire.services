# v2.0.x Planning

Planning document for the v2.0.x release line -- its theme, its sprints, and how a release is made.
The concrete work of each sprint is in that sprint's own task list.

Scope: esquire.services and esquire.explorer on the 2.0 line, and the two products they are built
on, Armoury and Herald. esquire.ui.lib and esquire.db.seed are not part of the line; it uses them as
they are on 1.2.

---

## Release line so far

| Version | Date | Headline |
|---|---|---|
| **v2.0.0** | 2026-10-18 | The split -- the shared libraries and the messaging bus become products of their own (Armoury, Herald); Esquire takes them from GitHub Packages, and the build, the local deploy and the cloud deploy run the 2.0 line from `develop2` |

---

## Theme -- the v2.0.x horizon

The goal of the line and its horizons are in [v2.0.x Goals](v2.0.x.Goals.md). Each sprint is named
here by its headline; its work is in its own task list.

The 1.2 plan named the first step v1.3.0: the messaging bus as a product of its own. It became
v2.0.0.

**The 1.2 line goes on in parallel.** Every step of the 2.0 work is additive: nothing on 1.2 is
renamed or restructured.

After v2.0.0 there is no fixed next sprint. What follows is drawn from the
[continuing-development backlog](Esquire.ContinuingDev.md) when the sprint opens.

---

## Sprint cadence

### Version scheme

The same form as the 1.2 line, **`vMajor.Minor.Micro-YYMM.DDHH`**, with Major `2`. The 1.2 rules
hold: Micro identifies a sprint, and the build extension identifies a commit within it.

Each product versions by itself. Armoury and Herald start at 2.0.0, to match the line they were
born in.

### Cadence rule

The same rule as the 1.2 line: every change is organized as a sprint with its own Micro version and
one headline scope item. Minor unrelated changes that are ready at the same time are folded in.

### Branches

| repository | 2.0 line | 1.2 line |
|---|---|---|
| `esquire.services` | `develop2` | `develop` |
| `esquire.explorer` | `develop2` | `develop` |
| `armoury` | `develop`, archived as `release/v2.0.0` | -- |
| `herald` | `main` | -- |

The two Esquire repositories carry both lines, each on its own branch; the 2.0 branch keeps the
whole commit history of the repository. Armoury and Herald started with no history -- one initial
commit each -- and the record of what each module was before 2.0 is in its `changes.txt` and its
source history headers.

Each release is tagged in its repository.

## Non-sprint continuous activity

These run alongside every sprint as routine work, not as headline scope.

### Documentation suite

Each product documents itself, in its own repository. Esquire's documents describe Esquire, and link
to Armoury and Herald for the parts that are theirs.

### Testing

**Gatling (Java DSL)** stays Esquire's standard for integration, stress and load testing. The
harness itself is `armoury-hauberk`; Esquire's simulations live in the services repository's
`hauberk` module and are built on it. Any sprint can add simulations and assertions as a routine
deliverable, the same way it maintains documentation. Reference: `doc/Esquire.TestingStack.md`.
