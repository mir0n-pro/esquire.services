 Esquire v1.2.8 -- sprint tasks
==============================

1. Access log (access-denied / failed-attempt logging)
   - Its OWN concern -- NOT part of the entity audit (AuditLoggingStack).
   - Gap: current audit logs only COMMITTED successes; a permission denial throws before
     xyRod.post() -> denied/failed attempts never reach a *_log.
   - Goal: record who attempted what + was denied.
   - Gate today: EsqRolesStorage.isAdminCmdPermitted() (keySmith / enyMan / pacMan POST writes).
   - Approach open: separate x-Rod-based access-denied component OR a uniform denied-log pattern across services.

2. Pluggable transport layer
   - Lift the x-Rod fan-out transport into a clean pluggable SPI (producer + consumer side).
   - Today: if/else per producer AuditConfig (x-rod.bus.transport=activemq|kafka; redis as a producer
     dispatcher seam); IRodDirector already makes the consumer transport swappable.
   - Goal: one seam so a transport (ActiveMQ / Kafka / Redis / next) plugs in uniformly -- no per-service branching.

   SOLUTION (built):
   - Transport SPI (common.transport): ITransportProvider { openPublisher / openConsumer over the neutral
     TransportMessage; supportsConsume() }. CLASS-NAME-DRIVEN, ZERO vendor constants in the framework: the
     config value (transport.provider) is a bare name -> the class pro.mir0n.esquire.tp.<name>.TransportProvider
     (convention) OR a full class name (any value with a dot); resolved reflectively + cached
     (TransportProviders.resolve). A new transport plugs in by dropping its jar on the classpath + naming it in
     config -- no framework-code change. Role-split settings PublishSettings (xy) / ConsumeSettings (xx) carry
     endpoint + identity (service/ctrl/client-id) + a generic params map (each provider reads its OWN vendor
     knobs by key: redis max-len, kafka group-id) -- so vendor params extend freely with no typed subclasses.
   - Per-transport modules (each is ONE class, pro.mir0n.esquire.tp.<name>.TransportProvider, builds its OWN
     broker client from settings.endpoint(), off spring.* -> the audit bus is independent of the KC/broadcast
     brokers): tp-activemq (queue), tp-kafka (topic), tp-redis (stream; producer-only -> supportsConsume()=false).
     The shared JMS helper messaging.jms.Utils moved to tp-activemq so common stays transport-vendor-free.
   - Unified bus-centric config: esquire.audit.x-rod.transport.{provider,endpoint,service-id,ctrl-id,client-id,
     publisher-pool-size,concurrency} + per-vendor groups transport.<vendor>.* (redis.max-len, kafka.group-id).
     BLANK provider = in-process (write the *_log here, option b). The SAME block is read by every producer AND
     the xxRod consumer (xxRod = universal consumer: carries all tp modules, resolves the configured one by name,
     and stays idle for a producer-only transport via supportsConsume()).
   - x-Rod transceiver (common.xrod): IXRod = one pod with BOTH legs (post/transmit + submit/receive). XRod folds
     the former XYRod feed + XXRod pool into ONE class -- the WIRING (XRodSettings.outbound / receiveWorker)
     decides post-only / listen-only / both (in-process = both, outbound = this::submit). CLASS-NAME-DRIVEN via
     rod-class (XRods.resolve, convention pro.mir0n.esquire.common.xrod.<name> or full class name; default XRod).
     The separate XXRod / XYRod are REMOVED (dead code gone).
   - The one destination (ROD_AUDIT) + AuditRod's TRANSPORT_*/MODE_* constants collapsed away; the dead tp
     auto-config beans + RedisPublishSettings/KafkaConsumeSettings + RodEventCodec.toJson/fromJson removed.
     Producer/xxRod dep dedup: direct transport starters dropped (provided transitively by the tp modules).
   - Verified: full unit suite + the real-broker Testcontainers IT green; e2e 35/35 across ALL FOUR audit
     topologies -- in-process / activemq / kafka / redis -- with audit landing in the right sink each time
     (in-process & activemq/kafka -> esq_*_log; redis -> the stream).
   - FINAL doc home (sprint end): a section in Esquire.AuditLoggingStack.md.
   - LEFT FOR LATER (step 2): fold the entity-broadcast + KC request/response buses onto the same seam.

3. System entity flag (anti-deletion)
   - A "system" flag on an entity (office / user) that PREVENTS deletion.
   - DB-set ONLY (seed scripts); not editable by anyone, anywhere; NOT visible on the GUI.
   - Enforced at the service (or DB) level; ties into the delete pre-checks.
   - Protects: root system + its users, and the seed Test House office + its users.

   SOLUTION (built):
   - Schema (db.seed, both vendors): new column ORG_SYSTEM_FLG / USR_SYSTEM_FLG
     VARCHAR(1) DEFAULT 'N' NOT NULL + Y/N CHECK constraint (create/tables.tab + tables.cc),
     mirroring the existing USR_DELETED_FLG convention.
   - Seed (db.seed fill/initial-entities.sql, both vendors): a "System entity flags" block sets
     'Y' on the protected set -- org 1 (root Esquire) + org 14 (Test House); users 4,5 (root
     System Administrator + Super Vizor) + users 15,16,17 (Test Drivers under Test House).
     DB-set only; no insert/update path ever writes the flag, so app-created entities default 'N'.
   - JPA (generic, NOT DTO): systemFlg added on the EsqEntityJpa base -> all 5 subclasses inherit
     it, but only Org and Usr SELECT the column (enyMan postgres/oracle-entity.xml detail +
     detailForUpdate queries + EsqOrg/EsqUsrJpaMapping); Acct/Address/Person leave it null.
     systemFlg is NOT in fillMap() -> never an audit-log asset.
   - Enforcement: a guard at the TOP of common ValidatorFactory.validateDelete() throws the
     existing DeleteRestrictedException (HTTP 409) when systemFlg='Y'. This is the single seam
     OrgService.deleteOrg + UsrService.deleteUsr already call before deleting (enyMan inits the
     factory with null biz-validators, so the guard precedes that early-return). Delete-only --
     update/move are unaffected. No DB triggers (seed stays trigger-free).
   - Test: common ValidatorFactoryTest -- systemFlg 'Y' throws, 'N'/null pass.
