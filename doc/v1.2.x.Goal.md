# The goal, and what Esquire is

---

## The goal

> Take the ordinary, widely used technology stack (a relational database with JPA, Spring Boot,
> Node.js with Angular, Grafana/Prometheus observability) and make **everything that stack makes
> possible**, in order to build **a hybrid REST and event-driven engine** on an **open architecture**
> (where every place can be filled by a different vendor) running as a **microservice
> infrastructure** that answers all **fifteen factors** of the cloud-native application, from
> API-first to telemetry and authorization.

Nothing exotic was chosen. The whole point was to show how far the ordinary stack goes when it is
used to its full extent.

---

## 1. The stack -- what was made possible from each part

**What Esquire is, and what it runs on.** Esquire itself is the **seven services** plus the
**browser tier** -- seven being the full split; the same services compose into five programs, or four,
without changing what they are -- the Node front-door and the Angular explorer. Everything underneath is
infrastructure it attaches to: the message broker, the database, the identity server, the
observability stack, the ingress, and Kubernetes itself. Those are named by configuration and can be
exchanged (factor 8 -- backing services); they are not parts of Esquire.

| Part of the stack | What Esquire got out of it |
|---|---|
| **Relational database + JPA** | One schema on two database brands (PostgreSQL, Oracle), each with its own query set; seed and versioned upgrade scripts; the entity tree and the audit tables in the database itself. JPA stays in the data layer only -- the services never see it. |
| **Spring Boot** | Seven services in the full split -- fewer when composed -- the gateway among them; wiring stated explicitly rather than guessed by the framework; routing, sign-in checking, health and readiness, timeouts and fail-fast, metrics -- all the same in every service. |
| **Node.js + Angular** | A Node front-door that keeps the token out of the browser (the browser holds only a session cookie); an Angular explorer and a shared component library whose screens are laid out from what the server says the entity is. |
| **Grafana/Prometheus observability stack** | One common way to see the running system: metrics and business counters, dashboards generated rather than hand-drawn, health alerts, plus collected logs and traces that follow one request across services and across message hops. |
| **The Esquire Messaging Bus** *(home-grown)* | The one part of the stack Esquire wrote itself, because nothing off the shelf filled the place: a subframework that **wraps the transport vendors and gives the application layer one uniform interface** for asynchronous messaging. A service never opens a broker connection of its own -- it asks one facade for a bus by name and role. |

The first four rows are ordinary technologies anyone can pick up. The last one is ours, and it is what
holds the rest together, so it is worth stating what it is:

- **One uniform interface for the application layer.** A service does not open a JMS connection, a
  Kafka producer or a Redis client. It asks the facade for the messaging end of a named bus, and gets
  the same shape every time -- send, receive, request, reply.
- **The vendor is wrapped, not chosen.** Each transport arrives as a drop-in driver module; a
  deployment carries only the drivers it uses, and the framework itself names no vendor. ActiveMQ,
  Kafka, Redis, Amazon SNS, Amazon SQS and Amazon Kinesis fit today.
- **A declared bus topology instead of a point-to-point mesh.** Every bus is declared once, in one
  shared catalog, rather than each service holding its own knowledge of brokers, queues and clients.
  Adding a bus is one entry in that file; adding a vendor is a driver on the classpath and a setting.
- **Both messaging shapes, plus a local one.** Broadcast (many senders, many listeners),
  request/response (a two-node round trip), and an in-process form for a leg that applies events
  inside the same service.

Full reference: [Esquire Messaging Bus -- Framework](Esquire.MessagingBus.md).

## 2. What it builds -- a hybrid engine

The engine is **hybrid by design**: one system with a request/response face and an event-driven
face, not two systems bolted together.

- **REST** -- the request/response face: the gateway, the service APIs, the front-door for the
  browser.
- **Events** -- the event-driven face: entity broadcast, request/response over queues, the audit
  stream. Inside the framework this face is carried by a subsystem of its own, the **Esquire
  Messaging Bus** -- one front door per service, one topology description, delivery and retry
  handled underneath.

Hybrid means the two are not layered one on top of the other and not kept apart. A business
operation can arrive as a call and continue as an event, cross services either way, and keep its
identity the whole way -- the same request is followed from the browser through the calls and
through the message hops. The choice between a call and an event is a design decision per
operation, not a boundary you have to cross.

The event side is a subsystem, not the goal. It sits behind the same kind of seam as everything
else in the framework, which is why the transport under it can be exchanged without the services
noticing.

## 3. How it is built -- open architecture

Every place where a product could lock you in is a slot with more than one thing that fits it:

| Slot | What fits it today |
|---|---|
| Database | PostgreSQL, Oracle |
| Message transport | ActiveMQ, Kafka, Redis |
| Identity | Keycloak, over standard OIDC |
| Sign-in pattern | Four working ones (browser front-door, plain token, and two token-relay patterns) |
| Audit handling | Six selectable strategies, with its own writer service |
| Where it runs | Docker, local Kubernetes, cloud Kubernetes (OKE) |
| How many programs it runs as | Eight, five, or four -- the same code, the same settings |

Extending means adding a driver behind an existing seam, not changing the services. That is the
test of "open": the service code did not move when the vendor did.

And it runs as a real microservice infrastructure -- containerized services, charts per target,
services running redundantly across machines, automatic build and test, deploy to a test cluster,
human-approved cloud release.

### The split is a deployment choice

A microservice split is usually a decision taken once and lived with. Esquire treats it as a **setting**: the
services can be **composed** -- several of them embedded as modules inside one program -- and the same code,
built the same way, runs as eight programs, as five, or as four. Nothing is forked, and nothing is rewritten
for the smaller shape.

**What composing keeps.** The parts that make it a framework do not move:

- **The same artifacts.** One build, one set of settings. There is no compact variant of the code to maintain.
- **The same contracts.** A caller sees the same REST paths and the same answers; it cannot tell which shape
  it is talking to.
- **The same authorization.** Tree-shaped scope and role rules resolve exactly as before.
- **The same messaging.** A hop that crossed the network becomes a call inside one process, through the same
  seam -- the bus decides that, not the application code.
- **The same visibility.** Metrics, logs and traces stay attributed per service, so a composed program still
  reports as its members.
- **The same audit trail.**
- **The way back.** Composing is reversible; splitting again is a redeploy, not a migration.

**What composing costs.** These are real, and they are the reason the full split still exists:

- **Deployment is shared.** Members of one program are released together; you cannot ship one alone.
- **Scaling is shared.** You add a copy of the whole program, not of the one member under load.
- **Failure is shared.** One process means one crash: its members go down together, and there is no bulkhead
  between them.
- **Resources are shared.** A member that is heavy on memory or threads takes them from its neighbours.
- **Runtime choice is shared.** One JVM, one set of library versions, for every member in the program.

The trade is deliberate. A large installation pays for isolation and gets it; a small one should not have to
run seven programs, a broker, an identity server and a database to keep a backoffice. The framework does not
argue for one shape -- it makes the shape a decision taken at deployment, by whoever is running it.

## 4. The fifteen factors

"Microservice infrastructure" is a big claim, so here it is checked against a published list rather
than asserted: the **15-factor application** (Kevin Hoffman, *Beyond the Twelve-Factor App*) -- the
original twelve factors reworked, plus **API first**, **telemetry**, and **authentication and
authorization**.

| # | Factor | How Esquire answers it |
|---|---|---|
| 1 | One codebase, one application | One module per service, each built and released on its own. They share a repository -- the build and the release do not. |
| 2 | API first | The service contract comes first: the gateway routes, the entity APIs, and the bus topology are all described before anything calls them. The UI is laid out from what the server says the entity is. |
| 3 | Dependency management | Declared per module -- Maven for the services, npm for the browser side, with the shared UI library consumed as a versioned package. |
| 4 | Design, build, release, run | Four separate steps in the pipeline. A release is a stamped, immutable image; running it never rebuilds it. |
| 5 | Configuration, credentials, and code | Configuration comes from the environment, never from the code; one configuration reference covers every service; no credentials in scripts or images. |
| 6 | Logs | Every service writes one structured event stream to standard output and nothing else. Collecting, storing and searching them is somebody else's job. |
| 7 | Disposability | Services start fast and shut down cleanly, finishing what is in hand before they go. |
| 8 | Backing services | The database, the broker, the identity server and the caches are all attached resources named by configuration -- which is what makes the vendor slots in the table above possible. |
| 9 | Environment parity | The same images and the same charts run on Docker, local Kubernetes and cloud Kubernetes -- and a parity check compares the cloud settings against the local ones so they cannot quietly drift. |
| 10 | Administrative processes | One-off jobs -- database seeding, forward-migration patches, load runs, switching observability on and off -- ship with the system and run against the same release. |
| 11 | Port binding | Each service serves its own port and depends on no outside web server. Health and metrics sit on a separate port that is not reachable from outside. |
| 12 | Stateless processes | No state is kept in a service between requests. The one in-memory cache is a copy that repairs itself from the database and can be thrown away at any moment. |
| 13 | Concurrency | Scale out by running more copies of a service, spread across machines, with sized worker pools inside each. How many is a setting, not a design limit. |
| 14 | Telemetry | The same metrics, logs and traces from every service, one request followed from the browser through the calls and the message hops. |
| 15 | Authentication and authorization | The framework's centre of gravity: an identity server over standard OIDC, four working sign-in patterns, and authorization resolved from the position in the tree. |

Two places where the answer is "yes, with a note", stated rather than hidden:

- **One repository, many services** (factor 1). Each service is its own module and builds, versions
  and deploys on its own -- the parent/child project structure even allows a separate version per
  service. What a service does not have is a repository of its own.

  Esquire does split by repository -- but along the **kind of thing**, not along the service:

  | Repository | Why it stands alone |
  |---|---|
  | `esquire.ui.lib` | A published package. A package has to live in its own repository -- that is how package hosting works. |
  | `esquire.explorer` | The browser side: the frontend components and the tests that drive them. |
  | `esquire.db.seed` | Database work only: schema and data scripts. |
  | `esquire.services` | The microservices. |

  Inside that last one the services stay together, and the reason is the hosting, not the design. One
  service per repository is what we would want, but a framework also needs one place that holds the
  parts together -- and GitHub has no hierarchy for repositories: there is no parent repository, no
  nesting. Splitting the services apart means losing the single coordination point for the framework
  as a whole.

  The cost of the choice is real and worth stating: a change to one service is still a commit to the
  repository that holds all of them, and per-service versions -- possible through the project
  structure -- no longer line up with how the repository is laid out. That mismatch is extra
  complexity to carry.
- **Database per service** -- **answered in substance, not by splitting the engine.** This is not one
  of the fifteen (it comes from the microservice pattern literature), but it is the first thing a
  reader will ask, so it is answered here.

  The factor is about each service owning its own data, not about giving each service its own
  database product. Esquire already keeps several stores apart: **sign-in data** lives in the
  identity server's own database, the **business tree** lives in a cache inside the tree service, and
  the **audit tables** are fully decoupled from the business schema -- where they are put is a
  deployment choice.

  What is left -- the entity, credential and accounting services -- shares one business schema, and
  inside it each of them works on its own set of tables. Their working areas do not overlap.

  Sharing one schema there is a decision, not a leftover. A relational database keeps data consistent
  for you, and that is exactly what business records need. Splitting the same data into isolated
  database instances means giving that up and building special machinery to hold consistency across
  them -- a hard problem, taken on for no gain here.

## What Esquire Frameworks is

The goal is met: **the ordinary stack, used to the end of what it can do.**

- A tree that is also the authorization model -- put a hierarchy on it and visibility, positional
  authority and entity behavior come with it.
- Entities that describe themselves -- the server states the fields, rules and commands once; the
  UI reads them at runtime.
- A hybrid engine -- a REST face and an event-driven face, both live, both vendor-neutral
  underneath.
- Highly available -- every service runs redundantly, spread across machines, so losing one machine
  keeps the site up.
- Observable the same way everywhere -- the observability stack can be switched on in any
  environment, at any moment. Whether it is left running is a resource decision, not a capability
  one: the development environment is kept light so it can be rebuilt quickly, and the public demo
  is kept cheap to run.
- Released by pipeline, and live in production at https://esquire.mir0n.pro.

> Everything the framework promises, it does -- in a running deployment, on three targets, with the
> evidence in the open.
