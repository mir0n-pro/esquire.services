## Theme — the v1.2.x horizon

The v1.2.x line set out to take the framework first stood up in v1.2.2 — the complete vertical slice on the traditional stack (PostgreSQL + microservices + JPA + REST + Node.js + Kubernetes) — and apply that same stack to the solutions postponed in v1.2.2, filling the gaps that deep testing and architecture work surfaced. In short: do all possible to let the framework cover the full stack.

**The end of the horizon is now visible.** With v1.2.9 complete, only two sprints remain in the v1.2.x line:

- **v1.2.10 — Resilience / Durability.** The Kubernetes redundancy & resilience features (OKE HA is live; the auKeep competing-consumer replicas are designed, validation pending), durability hardening of the messaging path, and the loss-visibility work carried over from v1.2.9.
- **v1.2.11 — Observability.** Apply the observability services available in OCI/OKE to the cluster — metrics, dashboards, and service-level visibility (JMX per service, JMX-based dashboards, a remote services console).

After v1.2.11 the v1.2.x horizon closes and the line rolls to **v1.3.0**.

**The Messaging Bus Framework.** Its introduction lands inside the v1.2.x line: the vendor-agnostic Messaging Bus subframework was extracted in v1.2.8 (`esquire-messaging` plus the `tp-activemq` / `tp-kafka` / `tp-redis` transport drivers), and it is under continuing development through the remaining sprints — the v1.2.9 per-service front-door, start-up lifecycle, health and robustness work, and the v1.2.10 durability hardening. **v1.3.0** then externalizes the Messaging Bus Framework into its own product / repository — a standalone subframework backing the Esquire Application Frameworks, rather than a module living inside the services repo.

The v1.2.x line is the sprint-by-sprint walk to that goal — one Micro version at a time, each with a single headline scope item.

## Sprint cadence

### Version scheme

Esquire releases follow the form **`vMajor.Minor.Micro-YYMM.DDHH`**:

- **Major** (`1`) — generation of the framework.
- **Minor** (`2`) — horizon within the generation.
- **Micro** (`3`) — sprint within the horizon. Conventionally this digit is used as a build counter; in Esquire it identifies a sprint instead.
- **Build extension** (`-YYMM.DDHH`, EST timezone) — identifies an intermediate commit *within* the sprint. Each meaningful code change during the sprint advances this stamp; it is not a recompile counter for unchanged code. `DDHH` is day-of-month + hour-of-day.

So `v1.2.3-2605.0512` reads as: *generation 1, second horizon, third sprint, intermediate commit at 12:00 EST on the 5th of May 2026*.

### Cadence rule

Within the v1.2.x horizon, every system modification is organized as a **sprint with its own Micro version**. Each sprint has one headline scope item — the reason for the version bump — and may fold in **minor unrelated changes** that were ready at the same time and are too small to justify their own sprint.

Example: **v1.2.3** is the BFF sprint. Mobile pointer-device support in `esquire.ui.lib` (a small unrelated change ready alongside) is folded into the same v1.2.3 release rather than waiting.

This keeps the versioning meaningful (the headline tells you what the sprint is *about*) while letting the release stream remain frictionless for incremental improvements.

### Branch flow

Each sprint follows the same git workflow across all four repositories:

1. Work happens on `pending-v1.2.X`.
2. When the sprint is ready: PR / merge `pending-v1.2.X` → `develop`.
3. Finalize on `develop` (release notes, `changes.txt`, source-file history headers, version stamp).
4. Tag `v1.2.X` on `develop`.
5. Create archive branch `release/v1.2.X` from the tagged commit.
6. Create the next sprint's `pending-v1.2.(X+1)` branch from `develop`.
7. Delete the old `pending-v1.2.X` branch.

## v1.2.3 — BFF sprint (complete, 2026-05-08)

Production live at https://esquire.mir0n.pro behind the new BFF tier. See the
["v1.2.3 — complete" section in the services README](../README.md#v123--complete-05082026)
for the prose milestone summary; this section keeps the planning record.

### Headline scope (delivered): BFF for REST + Node.js

- New tier `explorer/backend/` — Express + openid-client v5; OIDC code+PKCE; HttpOnly +
  SameSite=Lax cookie session; in-memory dictionary cache; baked SPA on the same image.
- KC `esq-angular` client converted public → confidential in place; KC moved from `/auth`
  to `/kc-auth` (BFF reserves `/auth/*` for its own login/callback/logout/me endpoints).
- Gateway became `ClusterIP` only — no longer publicly reachable. Only the BFF reaches it
  via the in-cluster service. Old `esquire-frontend` chart retired.

### JWE — investigated and dropped

The shelved 2026-04-20 JWE work was not revived. Empirical testing against stock Keycloak 26
proved KC does not encrypt access tokens at the standard `/token` endpoint regardless of
client configuration. The BFF cookie model meets the original "browser cannot see/modify
token" goal differently — by **never giving the browser the bytes**, instead of encrypting
what it holds. All gateway-side JWE artifacts were removed. Full record in
[doc/keyCloak-gateway.JWE.md](keyCloak-gateway.JWE.md).

### Folded-in minor changes (delivered)

- **`esquire.ui.lib` — mobile pointer-device support.** `EsqResizeDirective` and
  `EsqDialogResizeDirective` converted from mouse events to pointer events; touch and pen
  now work on real mobile. Touch-friendly handle sizes; `setPointerCapture` for reliable
  drag tracking.
- **Local k8s rebuild scripts.** `k8s-rebuild.bat` (per-target rebuild + tag-aware deploy)
  and a tag-aware `k8s-up.bat` work around Docker Desktop's kubelet `:latest` digest cache.
  `compose-rebuild.bat` mirrors the same flow for the compose path.
- **OKE postgres ops access.** `oke-pg-forward.bat` exposes the in-cluster Postgres on
  `localhost:25432` for pgAdmin4 (deliberately distinct from `5432`/`5433`).

### Carry-over to v1.2.x backlog

- **biztree + kcmaster: switch deployment strategy to `Recreate`.** ActiveMQ enforces
  clientId uniqueness across active connections; with k8s default `RollingUpdate` the new
  pod can't connect while the old pod still holds the clientId, deadlocking the rollout.
  Hit during the v1.2.3 OKE cutover. Manual workaround: `kubectl delete pod <old>` to
  release the clientId. Long-term fix: switch those two charts to `strategy: Recreate`.
- **Java pure-REST integration test playground.** Promoted to v1.2.4 headline scope
  (see "v1.2.4 — stress-test sprint" below).
- **Alternative OAuth IAS support.** Stock Keycloak's access-token signing/formatting is
  hardcoded in `DefaultTokenManager` with no SPI seam for format changes; access-token
  JWE on `/token` is not achievable without forking KC core (per v1.2.4 hauberk sprint
  investigation; see `doc/keyCloak-gateway.JWE.md`). To unblock end-to-end token
  encryption when / if it becomes a priority, plan for an alternative IAS that ships
  JWE natively. Concrete candidates:
  - **Auth0** — APIs can be configured to encrypt access tokens via JWE Compact
    Serialization, all grant types, JWKS-based key exchange.
  - **Okta** — Custom Authorization Servers support configurable encryption keys
    + algorithms for access tokens.
  - **ForgeRock / PingFederate** — heavier products, included for completeness.

  The preserved gateway-side `JweAwareJwtDecoder` + `/jwe-jwks` design is consumer-side
  agnostic and would work against any of these without changes -- swap the issuer URL.

## v1.2.4 — Haubergeon sprint (complete, 2026-05-12)

Originally scoped as "stress-test suite (Haubergeon)"; the harness shipped and stayed
honest to that scope — but Haubergeon turned out to be a vehicle, not the destination.
The real outcomes split into five areas: the testing harness itself, an answer to the
"how do we cleanly authorize without JWE" question, the matrix tooling that exposes
where time is spent under load, a clean playground identity model in db.seed, and the
OKE deploy shape (gateway returns to public exposure on its own ingress).

### Delivered scope

**Stress-test harness (Haubergeon itself):**

- `explorer/hauberk/` Gatling 3.13 (Java DSL) module — pure-REST client, OAuth2
  `client_credentials` grant against three certified KC clients: `esq-hauberk`
  (Plain JWT), `esq-hauberk-S` (Vanilla Token Relay), `esq-hauberk-M`
  (Phantom Token Relay). Future slot `-L` reserved.
- Java main (`HauberkCli`) with picocli — subcommands `run`, `list`, `summary`,
  `diff`, `help`. Single fat jar (`target/hauberk.jar`) via maven-shade-plugin;
  thin `hauberk.cmd` launcher adds the `--add-opens` JVM flags Gatling needs.
- Chains, Simulations, and SuperLoad shape knobs (`super.*.workers`, durations)
  all driven by `hauberk.properties` with overlay support (`hauberk-S.properties`
  for the Vanilla Token Relay variant; future `hauberk-M.properties` / `-L.properties`
  plug in identically). Sims live as `src/main/java` (compile-scope; programmatic
  Gatling launch via `io.gatling.app.Gatling$.MODULE$.fromArgs`).
- Robustness: `RefreshableToken` auto-refresh past the 5-min TTL cliff;
  `HealthPreCheck` (KC + GW + auth-path probes) fails fast pre-sim.

**Auth protocol stack (four certified patterns, JWE finally parked):**

- KC's access-token JWE was re-tested under `client_credentials` (the second
  standard grant); same conclusion as v1.2.3's auth-code test — KC's
  `DefaultTokenManager` has no encryption path on `/token` regardless of
  configuration. JWE parked until v1.3+ (alternative IAS or KC roadmap movement).
- **BFF** (v1.2.3) — browser holds opaque cookie, token server-side
  on BFF. Untouched in v1.2.4.
- **Plain JWT** — gateway validates JWS locally against KC's JWKS.
  Standard, zero overhead, no claim-hiding. Default for service-to-service
  callers (`esq-hauberk`, `esq-rest`, `esq-kcMaster`).
- **Vanilla Token Relay** (new) — client sends `Authorization: Basic
  <id:secret>` (no token on the wire); gateway brokers a full JWT from KC via
  `grant_type=client_credentials` using the client's own credentials, caches
  per `client_id`, rewrites Authorization to Bearer. Strongest claim-hiding for
  non-browser callers (client physically holds no token). Inbound-Bearer
  enforcement rejects azp-in-allowlist tokens (architectural-bypass closed).
  Certified client: `esq-hauberk-S`.
- **Phantom Token Relay** (new) — client sends a stripped Bearer JWT;
  gateway exchanges via RFC 8693 token-exchange (authenticated as the new
  confidential `esq-gw-exchange` client) for the full claim-rich JWT, caches
  per `jti`. Keeps the standard OAuth Bearer flow at the client; adds token
  portability across multiple gateways. Certified client: `esq-hauberk-M`.
- Full record (block diagrams, sequence diagrams, decision matrix, "patterns we
  deliberately don't use" section) in
  [doc/keyCloak-gateway.JWE.md](keyCloak-gateway.JWE.md).

**Observability protocol — four-layer measurement:**

- Gateway timers re-architected. `RequestTraceFilter` moves from
  `GlobalFilter @Order(1)` (post-security) to `WebFilter @HIGHEST_PRECEDENCE`
  (pre-security). `X-Response-Time` now covers the full envelope including
  Spring Security work — auth-layer time visible.
- New `InnerTimerFilter` (`GlobalFilter @Order(0)`) emits `Esq-Gw-Inner-Time` =
  gateway's downstream-call-only window. Delta = gateway's own overhead.
- Service-tier headers renamed: `Esq-Service-Time` → `Esq-Srv-Outer-Time`;
  `Esq-Backend-Time` → `Esq-Srv-Inner-Time`. Future-extensible naming
  `Esq-Srv-Inner-{X}-Time` (e.g. `-DB-`, `-JMS-`, `-Cache-`) for inner-aspect
  decomposition; the umbrella `Esq-Srv-Inner-Time` always stays.
- Esquire's standard CLI library locked: **picocli** (everywhere we need a CLI
  going forward, not just hauberk).

**Performance Matrix tooling:**

- `PerformanceMatrix` (in the hauberk module) wraps Gatling's
  `transformResponse` callback. Per-scenario CSV (super-sim produces N
  CSVs, one per parallel scenario; super-sim itself has no aggregate output);
  YAML-frontmatter preamble (simulation, scenario, client, kc_base, gw_base,
  start_utc); naming `<scenario>-<YYMMDDHHmmss>.csv` in `./metrics/` default
  (override via `--metrics-dir`).
- Per-URL grouping in summary + diff — explicit rejection of aggregate
  ("you cannot sum beer cans and chairs"). Only per-request-URL stats are
  honest; aggregate medians are sim-mix artifacts.
- `hauberk.cmd summary <csv>` and `hauberk.cmd diff <csv-a> <csv-b>` for
  post-hoc reading and A/B comparison.

**Realm-level access-token slim:**

- Stripped from access tokens (kept on userinfo/id_token where appropriate):
  email, email_verified, preferred_username, given_name, family_name,
  name, picture, locale, allowed-origins, acr (loa level), realm-roles
  (duplicate), resource_access (per-client), client_id / clientHost /
  clientAddress (service-account leak). 20 mappers' `access.token.claim`
  flipped at realm scope level — affects every existing and future client.
- esq_rootid removed (legacy from early design; not used).
- Final shape: `esq_uid` + `esq_rootpath` + `realm_access.roles` + standard
  registered (`iss`/`aud`/`exp`/`iat`/`jti`/`sub`/`typ`/`nbf`) + OAuth2-required
  (`azp`/`scope`) — 11 fields total, same shape for both grant types.

**Playground identity:**

- `db.seed` added: ORG `Test House` (org_pk=14, parent=root), USR
  `Test Driver` (usr_pk=15, kind=32 admin, `connectFlg=N`,
  `esq-hauberk@mir0n.pro`), USR `Test Driver S` (usr_pk=16, same shape,
  `esq-hauberk-S@mir0n.pro`), USR `Test Driver M` (usr_pk=17, same shape,
  `esq-hauberk-M@mir0n.pro`). All three with realmRoles SUPERVIZOR + TREE.
- KC service-accounts `service-account-esq-hauberk`, `-s`, and `-m` rewired:
  `esq_uid=15/16/17`, `esq_rootid=14`, `esq_rootpath="1.14."`. Test Drivers
  can see and modify only the Test House subtree; can't touch the rest
  of the tree.
- Hauberk config `playground.parent.id=14` — every office / user / account
  the hauberk creates roots under Test House.

**OKE deploy shape:** gateway returns to public exposure at
`https://api.esquire.mir0n.pro` (separate ingress host so it doesn't
collide with BFF's `/api/*`). Auth is JWT validation as before — any
KC-signed token passes, anonymous traffic rejected. BFF → gateway hop
stays in-cluster. Root URL (`/`) serves a polite HTML landing page
(`LandingController`) in place of the stock Spring 404.

**Race-condition repros (Phase 8 of the original plan):** two self-
validating sims (`RaceCacheLoadSimulation`, `RaceMoveCreateSimulation`)
reproduced the known cache-load + move/create-path races on compose.
Will serve as Phase 9 regression tests when the fixes land in v1.2.5+.
Full repro steps + numbers live in
[Race.Conditions.Repro.md](Race.Conditions.Repro.md).

### Deferred to v1.2.5+

- **Race-condition fixes (Phase 9).** Originally planned for v1.2.4 as the
  closing pair to the repros; scope-shifted to v1.2.5+ alongside broader
  architecture refinement. The repro sims stay armed and become the
  acceptance tests.

### JWE — parked

Stock KC's `DefaultTokenManager` has no encryption code path on `/token`
for any standard grant; the `access.token.encrypted.response.*` client
attributes are silently ignored. The path forward, if claim-hidden +
self-contained becomes a hard requirement, is to swap the IAS to one
that emits JWE natively (Auth0 / Okta / ForgeRock / Ping). The gateway-
side `JweAwareJwtDecoder` + `/jwe-jwks` lab is kept armed (code in tree,
keypair on disk, four JWE attrs on `esq-hauberk`) — one config flip away
from a re-test under a JWE-emitting IAS. Full three-pattern architecture
in [doc/keyCloak-gateway.JWE.md](keyCloak-gateway.JWE.md).

### Folded-in minor changes (delivered)

- **`esq_rootid` removed** from realm + user attributes (was legacy from
  early design; no code consumer).

## v1.2.5 — bizTree cache refactor sprint (complete, 2026-05-24)

*The sprING is over, long live the sprING!* — v1.2.4 closed; v1.2.5 shipped the full Taijitu.

### Headline scope: the "Taijitu" Supreme Ultimate Cache

bizTree's internal cache is rebuilt as the **Taijitu** — an anti-entropy double-buffer
with shadow promotion — to close the **cache-load race** repro'd in v1.2.4 (the Phase 9
fix deferred here). The external surface is unchanged: same REST paths, same JMS topic +
subscription, same cache interface. The new implementation slots in behind it, so the
refactor is invisible from outside.

This promotes the former **bizTree "night guard"** backlog item to active scope — the
"night guard" is now the Taijitu **night-watch sweep**: receive messages while loading
(Step 2), then monitor tree discrepancy against the DB with a decision-maker for what to
do when a discrepancy is found (Step 3 night-watch).

Progress:
- **Step 1 (done)** — stable REST + JMS entry points reduced to pass-throughs over a
  configurable `IBizTreeDirector` (legacy | yang | taijitu).
- **Step 2 (done, certified live)** — the "yang" single-monad director: one queue, one
  worker, two gates; events buffer during load and apply only after it succeeds, closing
  the race. Plus per-monad precomposed SQL.
- **Step 3 (done)** — the full Taijitu: two monads (yang + yin); a night-watch anti-entropy
  sweep that monitors cache-vs-DB discrepancy with a decision-maker for resolution;
  checksum-driven shadow promotion / role swap. Plus message-loss simulations (SWAP / TERMINATE)
  that prove the night-watch reacts to dropped JMS broadcasts.

Acceptance: the v1.2.4 race-repro sims (`RaceCacheLoad`, `RaceMoveCreate`) stayed armed and
became the regression tests — green.

Architecture: [doc/Esquire.BizTree.md](Esquire.BizTree.md).

## v1.2.6 — enyMan redundancy / race-8c sprint (complete, 2026-06-02)

A short, sharp sprint that made the platform safe to run multi-instance. See the v1.2.6 milestone
report (linked from the [README](../README.md#reports)) for the prose summary.

### Headline scope (delivered)

- **Instance-aware entity-id minting** — each enyMan instance mints IDs without collision, so the
  registry can run redundant.
- **Async move queue** — `/esq-move` returns a 202 async-ack; create events arriving mid-move are
  queued and their paths refreshed after the move completes.
- **kcMaster path-buffer** — closes race-8c (DB `ep_path` vs KC `esq_rootpath` divergence under a
  concurrent move + create).
- **bizTree event work-batching** — applies a backlog of cache updates in one transaction instead of
  per-event commits; ~3x broadcast-apply throughput under a move-cascade flood.
- **enyMan / pacMan decoupling** — account CREATE moved onto enyMan; pacMan is the accounting engine.
- Proven through the same Gatling race-repro harness (race-8b / race-8c).

## v1.2.7 — audit-logging + CI/CD sprint (complete, released to OKE 2026-06-10/11)

Two outcomes in one sprint: a pluggable audit subsystem, and the delivery pipeline that ships the
whole platform. Detail in [Esquire.AuditLoggingStack.md](Esquire.AuditLoggingStack.md) (the audit
design + stack) and [Esquire.GitHubActions.md](Esquire.GitHubActions.md) (the pipeline).

### Headline scope (delivered)

- **Audit-trigger decoupling** — the account funded-date stamp moved from a DB trigger to the pacMan
  service; the base seed is now trigger-free (triggers become an opt-in overlay).
- **The x-rod substrate** — a generic entity **fan-out** producer/consumer couple; audit is the first sink,
  replication / search-index are future sinks on the same producer. New standalone audit-writer consumer
  service.
- **Six selectable strategies** behind one seam, chosen by configuration: **(0)** none, **(a)** DB
  triggers, **(b)** in-process, **(c)** bus → consumer → SQL, **(d)** Redis Streams, **(e)** log-based CDC
  (out of framework scope). The bus path runs over **ActiveMQ or Kafka**; (c) is the default deploy
  topology on Docker and local k8s.
- **CI/CD pipeline established (GitHub Actions)** — hosted CI on every push/PR; self-hosted local-k8s
  deploy on `pending-**`; an approved OKE production release on a `pending-*` PR merged to `develop`.
  v1.2.7 was the first release deployed to OKE through the pipeline.

### Deferred to v1.2.8+

- **Pluggable transport SPI** *(DELIVERED v1.2.8)* — the per-producer if/else ActiveMQ/Kafka/Redis wiring
  was lifted into a clean transport-driver SPI; it grew into the full **Messaging Bus** subframework.
- **Access-denied / failed-attempt audit** *(postponed → v1.2.9+)* — the current audit logs only committed
  successes; a permission denial throws before the producer fires. Its own concern (an **access log**, not
  entity audit). Postponed out of v1.2.8; the v1.2.9 scope will be redefined shortly after the v1.2.8 release.

## v1.2.8 — Messaging Bus (complete, 2026-06-19)

Started as "hardening + extensibility"; the **pluggable transport layer** grew into the headline — the
messaging layer was lifted into a vendor-agnostic **Messaging Bus** subframework. Delivered:

1. **Messaging Bus** — the bus framework extracted from `common` into its own `esquire-messaging` module
   with pluggable transport-provider drivers (`tp-activemq` / `tp-kafka` / `tp-redis`); every cross-service
   conversation (entity broadcast, KC request/response, audit) runs over one uniform bus, the broker a
   per-deployment choice. Alongside it the keep stack split into `esquire-data-keep` (the generic engine)
   + `esquire-audit` (the audit rules), lifted out of `common`, and the audit-writer service `xx-rod` was
   renamed **auKeep**. (Realizes the parking-lot "Messaging bus — concept and abstract layer" item.)
2. **System entity flag** (anti-deletion) — a DB-set-only flag on office / user that prevents deletion;
   not GUI-visible; enforced at the service / DB layer; protects the root system + the seed Test House.

**Postponed out of the sprint:** the **access log** (access-denied / failed-attempt logging) — its own
concern, **not** part of the entity audit — carries forward to a later sprint.

## v1.2.9 — Hardening (complete, 2026-06-24)

A hardening sprint that tightened what the v1.2.8 Messaging Bus refactoring put in place. See the
["v1.2.9 — complete" section in the services README](../README.md#release-history) for the prose summary.

### Headline scope (delivered)

- **Bus front-door + lifecycle** — one entry point per service (the `MessagingBus` facade) with a defined
  start-up sequence (load + validate the catalog, build every x-rod paused, then open connections on
  readiness); each conversation's role is declared in configuration; a misconfigured service, or one naming a
  bus it does not have, fails fast at start-up.
- **Health & keep-alive** — every service forwards its bus-connection health to `/actuator/health`, split into
  readiness / liveness; a FIX-style alive protocol (opt-in heartbeat) catches an outage faster; auKeep also
  reports its keep database.
- **Robustness** — defensive message decoding (a bad field falls back to a default; an unknown wire-format
  version is refused); DB timestamp columns + lookup indexes; the SQL dialect derived from the datasource URL.
- **Wire-constant split** — the bus message-format constants moved out of `common` into `esquire-messaging`
  (`BusConstants`), so `common` carries no bus-wire definition.

### Carried over to v1.2.10

- **Loss visibility** — drop / failure counters at the silent message-drop points; begun in v1.2.9, folded
  into the v1.2.10 Resilience / Durability scope.

## Continuous activities (not sprints)

These run alongside every sprint as routine work, not as headline scope. They do not earn their own Micro version.

### Documentation suite

> "No one needs undocumented frameworks."  _Salvatore Sanfilippo (Antirez)_  

The documentation suite is itself a framework feature. Guides, tutorials, and AI prompts for Esquire-based implementations are continuous deliverables — defined and grown as required, not gated on a sprint. The concrete set of docs that constitutes the framework's documentation feature is to be established as the need surfaces.

Think about an **"Esquire Manifesto"** — the front matter of the documentation suite, the framework's principles stated as a handful of declarative tenets a reader can absorb in thirty seconds. Sketch:

1. **The tree is the authorization model.** The org chart and the access rules are the same artifact, not two artifacts that drift apart.
2. **Position grants visibility. Position grants authority.** Authority is not a global property of an account; it is a function of where you sit.
3. **Every entity has a kind.** Kind is the type — it determines structure, validation, available commands, and rendering. Behavior follows kind, not class hierarchy.
4. **Every entity has one ID, globally unique.** Across kinds, across branches, across services — an entity ID identifies exactly one entity. A reference is one number, never a `(kind, id)` pair.
5. **The entity defines itself.** Field layout, validation rules, available commands — declared once at the business layer; the UI listens at runtime.
6. **Solve the floor once.** The structural plumbing of every backoffice — users, permissions, audit, accounts, admin UI — is solved once so the product can be the actual point.
7. **No vendor stands between you and your data.** Database, broker, IAM, cloud — every external dependency sits behind a swappable adapter. Open source. Self-hostable. Yours.

### Testing

Esquire uses **Gatling (Java DSL)** as the standard framework for integration, stress,
and load testing. The hauberk sprint (v1.2.4) lays down the first Simulation set;
subsequent testing work — whatever the sprint, whichever the service — composes new
Chains and Simulations on the same Gatling foundation rather than introducing parallel
frameworks. Reference: `doc/Testing.md` (created in v1.2.4).

This is a continuous activity rather than a sprint headline: any sprint can grow the
testing surface (new Chains, new Simulations, new assertions) as a routine deliverable
alongside its primary scope, the same way each sprint maintains documentation.

## Beyond v1.2.x — parking lot

Items identified during v1.2.x but explicitly out of scope for this release line. Captured here so they aren't lost. Order is rough; some may move forward as parallel sprints depending on mood and contributors.

### Persistence layer

- Move out from JPA — use of **DABABERE** (DataBase BEan REpository framework, under development); comparison JPA vs DBBR.
- DB API isolation concept: CRUID vs procedural APIs, DB messaging patterns.
- Attempt to employ OpenAPI to generate DB API: Model + Queries + Repository classes.
- Extending the list of RDBMS targets: MySQL, MS SQL, Sybase.

### Messaging bus — concept and abstract layer

- Vendor-agnostic messaging as announced.
- Drivers: ActiveMQ first (broadcast and r/r), Redis second (broadcast).
- Broadcast server/client controllers — topic/stream based.
- Request/Response queue-based controllers.
- Request/Response queue-less controllers based on back-and-forth streams.
- Messaging Bus configuring.

### UI improvements (esquire.explorer + esquire.ui.lib)

- Nested-tree implementation of the same components — removes block.
- Filtering / search and pagination — for list views and for tree views.
- New **Options / Settings** item in the logon dropdown submenu, holding user-level preferences:
  - disable / enable / reset stored resizing cookies
  - disable / enable view of "deleted" entities
  - force bizTree cache validation *(gated on the v1.2.5 bizTree night-watch sweep landing — meaningful only once discrepancy detection exists)*
- Permission sysadmin UI tool — manage roles and permissions.
- Custom parameters sysadmin UI tool — manage the custom-fields dictionary.

### pacMan → pacMaxRay

- pacMax + xy-xxRay(s).
- Multithreaded event-driven account transaction processor.
- OODB — Object DB as the only place for account state synchronization.
- One virtual thread per account; queue as the entry point to each account.
- LMAX Ring (Disruptor) to distribute events from the messaging bus to the account thread; multi-producer → multi-consumer.
- Replication thread(s) for account change events (logs, account, transaction).
- PacMax with xyRay → Kafka (or any fanout stream) → xxRay → (esq2025, logs, transactions).
- M2M snapshot DB schema.

### Messaging API on pacMax

- Only messaging access to pacMax.

### WebSocket bridge/gateway to pacMan (open architecture)

- BFF: REST-messaging API route direct access.
- Async media facade (open architecture).
- WebSocket facade as the first implementation.

### Operational tooling
